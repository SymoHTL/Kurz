The case tables of `s.ToLower()` and `s.ToUpper()` (X3) are the version of the Unicode Character
Database that Rust's latest stable release pins as `char::UNICODE_VERSION`, generated as Rust's
`unicode-table-generator` makes them (section 12, the owner, 2026-10-31, "Rust's pin" and
"Generated, as Rust"). Nothing in the compiler reads the database: `tools/unicode_tables.py`
fetches UnicodeData.txt, SpecialCasing.txt and DerivedCoreProperties.txt of the version it pins,
refuses a file whose SHA-256 is not the one it pins, and writes `CaseTables.cs`, which the
emitter writes into a program that changes case. The gate `unicode-tables` runs the tool with
`--check`: red where the file is not what the files give, and PARTLY, which is red, where a file
cannot be fetched, since then nothing was compared.

## How to apply

1. Read the version Rust's latest stable release pins: `UNICODE_VERSION` in
   `library/core/src/unicode/unicode_data.rs` of the branch `stable` of rust-lang/rust. Nothing to
   do while it is the `VERSION` of `tools/unicode_tables.py`.
2. Fetch the three files of the new version from `https://www.unicode.org/Public/<version>/ucd/`
   and take the SHA-256 of each.
3. Put the version in `VERSION` and the three hashes in `FILES` of `tools/unicode_tables.py`, then
   run `py -3 tools/unicode_tables.py` (`python3` outside Windows, as in CI). It writes the file and prints every mapping and every code
   point of Cased and Case_Ignorable that changed, as `lower U+XXXX: old -> new`.
4. The pull request lists those lines in its description, and needs no question to the owner
   (section 12, "PR, no question"), as Rust takes a new version as no breaking change: the
   documentation of `char::UNICODE_VERSION`, read on 2026-11-01, says that the behaviour of some
   methods of `char` and `str` changes over time, as the standard library takes each new version,
   and that "This is *not* considered to be
   a breaking change". The tool refuses a mapping that leaves its plane, a mapping past the first
   two planes and a run that spans more than 256 code points, the forms its tables do not hold:
   such a refusal is a change of the tables' form, and a question for a design round before it is
   a line of code.
5. The suite's `CaseTests` reads the new tables on its own, and the record's sizes (section 12)
   are measured again where the counts of `CaseTables.cs` grew.

The tool keeps each fetched file in the system's temporary directory under its hash and reads it
from there while the hash holds: a machine fetches the three files, about 3.4 MB, again only when
its temporary directory has lost them, while the container of the `gates` job starts empty and
fetches them on every run, so that an outage of unicode.org turns every run of the job PARTLY,
and red. A file served with another hash is refused, not read: the tool holds each file to the
hash it pins, whatever unicode.org serves.

## Where the tables come from, and how they were checked

The tool takes the mappings as Rust's generator does: UnicodeData.txt's simple mappings, then
SpecialCasing.txt's mappings without a condition over them, a mapping to the code point itself
left out, and ASCII left to the standard library's own letters. It packs the mappings to one code
point into runs in Rust's two passes, consecutive code points with one delta, then lone code points
two apart. On 2026-10-31, for 17.0.0, the runs and the mappings to several code points it wrote
were those of Rust's `LOWERCASE_LUT` and `UPPERCASE_LUT` on its stable branch entry for entry,
184 and 197 runs and 1 and 102 mappings, with Rust's deltas read modulo 65536, as its `i16` holds
them. The two properties the final sigma reads are DerivedCoreProperties.txt's Cased and
Case_Ignorable, ASCII among them, the properties Rust's `is_cased` and `is_case_ignorable` read.
